# Supabase database setup

Never place a Supabase secret key or database password in the Expo app.

## Migrations

Each file in `migrations/` is run once, by hand, in the Supabase SQL Editor. The names start with the date and time each file was added (Supabase's own naming), so the folder lists them in the order to apply them; a fresh local database (the website's demo screenshots, `docs/WEBSITE.md`) applies all of them in this order.

| File | What it does |
| --- | --- |
| `20260904212310_initial_schema.sql` | The schema, policies and the private `journal-media` bucket. Afterwards `verification/verify_stage_6_2.sql` must report 15 public tables (16 once `ai_usage_limit` is applied), ownership/read policies for every table, and the private bucket. |
| `20260904212311_seed_prompts.sql` | The first prompt library; needed before saved prompts can sync (replaced by `prompt_library_v2` below). |
| `20260904212312_stage_7_2_ai.sql` | Adds the estimated minutes to daily prompts, for a database created before Stage 7.2. |
| `20260904212313_stage_7_3_settings.sql` | Limits the theme setting to dark or light (the old "system" becomes dark), for a database created before Stage 7.3. |
| `20260906002509_stage_8_1_trip_entries.sql` | Links entries to their trip (`trip_id`), for trip entries and synchronized trip deletion. |
| `20260925185959_stage_9_2_folders.sql` | Optional; run while no device has pending sync changes. Blocks deleting a folder that still has entries, moves the retired Travel and Other entries into Notes, and sets the default folders for new accounts. The app works without it. |
| `20260928204804_ai_usage_limit.sql` | Keeps the API's daily AI limit (30 new AI results per account per day) in the database, so a Railway restart or a second server instance does not reset it; users can read but never change their own counts. Until it is applied, the API counts in memory. Adds the 16th public table, `ai_usage`. |
| `20260928204805_entry_length_limits.sql` | Caps the size of regular entries (title 1,000, description 10,000, text 1,000,000 characters, body 5 MB, location 500), well above the app's own limits. The constraints are `NOT VALID`, so existing rows are not checked and applying it cannot fail. |
| `20261001234204_recently_deleted.sql` | Recently Deleted: deleted entries keep their row for 30 days (`deleted_at`). Check with `verification/verify_recently_deleted.sql`. |
| `20261002003139_mood_suggestion.sql` | Keeps the last AI mood suggestion with its entry (regular entries only). Check with `verification/verify_mood_suggestion.sql`. |
| `20261002183818_prompt_library_v2.sql` | The current prompt library (80 prompts), generated by `npm run prompts:sql` from `src/domain/prompts.ts`; safe to run again. |
| `20261002183819_reminder_default_on.sql` | The daily reminder is on by default for new accounts, at 20:00. |
| `20261008142031_account_storage_limits.sql` | Storage limits per account (security audit, 2026-10-08): at most 500 photos or 250 MB of photos and 50 MB of notes and other journal data, so one account cannot fill the free plan for everyone. At a limit, new photos and growing saves are refused (the app says "Storage limit reached: …" and keeps the change on the device), while deleting always works. Check with `verification/verify_account_storage_limits.sql`. The limits must match `src/domain/storage-limits.ts`. |

Add a new migration with the same naming (`YYYYMMDDHHMMSS_what_it_does.sql`) and a line in this table.

The live database has never recorded these files as applied: they were run by hand. So never run `supabase db push` against it, which would try to run every file again (and the first one fails on an existing database). If the Supabase command line is ever linked to the live project, first mark each file that was already run as applied with `supabase migration repair --status applied <timestamp>` (code review, 2026-10-08).

## Authentication URL configuration

In Authentication › URL Configuration:

- **Site URL:** `bunari://` — a real address. Supabase falls back to it when an email link fails (for example an expired link), so it must never be a wildcard.
- **Redirect URLs:** `bunari://**` — the wildcard belongs only in this allow-list. The app requests `bunari://auth/sign-in?link=signup` for sign-up confirmation (the app then shows Sign in with "Email confirmed" and does not sign in; user, 2026-10-09), `bunari:///` for email changes and `bunari://auth/reset-password` for password recovery.

The app turns any `error=` redirect into a readable "Link not valid" message, and unknown `bunari://` addresses open the app normally.

## Authentication settings

Set on 2026-10-09 (security audit, 2026-10-08); keep them this way:

- **Passwords** (Sign In / Providers › Email): minimum length 8, required characters "Lowercase, uppercase letters, digits and symbols". `src/lib/auth/password-rule.ts` must match. Existing passwords keep signing in.
- **Confirm email:** on. **Allow anonymous sign-ins:** off.
- **Sessions:** refresh-token reuse detection on, access tokens expire within 1 hour (3600 seconds).

The authentication emails are sent through Resend (`noreply@bunari.app`) with the templates in `email-templates/`; its README says which template and subject go where.
